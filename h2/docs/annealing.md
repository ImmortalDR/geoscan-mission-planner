# H2: имитация отжига

Веб-расчёт H1 → H2 → H3 и CLI `h2 plan` используют отжиг. Геометрия H1
не меняется: состояние задаёт БПЛА, порядок задач, вариант змейки и направление.
Критерий — `makespan` (от начала окна миссии до последней посадки, включая
ожидания и обслуживание) или `total_flight` (сумма длительностей вылетов).
В H2 секунды отсчитываются от начала окна в bundle. H3 независимо
пересчитывает метрики, учитывая более позднее начало светового дня; именно
его значение показывается после проверки в интерфейсе.
Полнота назначения важнее сокращения времени: пропущенные задачи нельзя
«улучшить», просто исключив их из метрики.

## Порядок расчёта

1. `FixedPlanEstimator` подробно считает допустимые проходы задач и пороги
   ресурса для возврата из любой точки. Перелёты и аварийный возврат оцениваются
   по консервативной сетке; модель и запасы описаны в [fixed-estimator.md](fixed-estimator.md).
2. Прежний H2 выполняет полный жадный проход без CP-SAT и LNS. Его план —
   начальное приближение. Дополнительно строится географический порядок
   ближайших входов задач.
3. Отжиг меняет вариант прохода, переносит задачу другому совместимому БПЛА,
   обменивает две задачи между БПЛА, переставляет задачу внутри маршрута либо
   обращает участок порядка вместе с направлениями задач (2-opt).
   Улучшение принимается всегда; ухудшение — с вероятностью `exp(-delta/T)`.
   Начальная температура получается из пробных ухудшений: медианный шаг
   принимается с вероятностью 0,65. Затем температура геометрически падает
   до 0,002 начальной.
4. Для каждой последовательности динамическое программирование выбирает
   разбиение на вылеты и посадочные базы, соблюдая ресурс, закрепления баз,
   непрерывность местоположения, обслуживание, окно миссии и световой день.
   Учитываются окна начала задач и временные запреты. Кэшируются неизменённые
   последовательности и префиксы вылетов. В общем случае с несколькими базами
   остаётся до восьми недоминируемых состояний на позицию/базу: это ограниченная
   эвристика, а не доказательство глобального оптимума. Для одной базы
   разбиение проверено сравнением с полным перебором разделителей вылетов.
5. Несколько различных лучших планов разворачиваются в подробные траектории.
   Выполняются полные проверки H2. Для конфликтов пробуются задержки обоих
   БПЛА, выбирается меньшая стоимость, затем безопасная задержка уточняется.
   Сдвигаются только необходимые последующие вылеты того же БПЛА с учётом
   обслуживания. Временные зоны учитываются по пересекающим их сегментам.
   После исправлений снова проверяются конфликты, окна и ресурс.
6. Выбирается лучший проверенный результат по фактической метрике и передаётся
   независимому H3. Только H3 может выдать `SAFE` и сертификат.

Полный исходный план также можно сохранить, если он лучше сеточного варианта
и проходит новый запас возврата по своим подробным точкам. Если полного
решения не найдено, более полный прежний план сохраняется для диагностики:
это `legacy_fallback`, он не выдаётся за полный или безопасный. Для такого
неполного плана новый запас возврата не заявляется как проверенный.
Недопустимые остаточные конфликты, перерасход ресурса и неназначенные задачи
не скрываются. Увеличение глубины не гарантирует решение любой сцены.

## Глубина и воспроизводимость

Seed по умолчанию **20260918**, в UI всегда этот же. Порядок обхода и число
итераций детерминированы. Остановка по прошедшим секундам не используется:
иначе загруженность сервера меняла бы результат. `time_budget_s` масштабирует
число шагов и является ориентиром объёма поиска, а не пределом всего расчёта.
Внешний worker по-прежнему имеет аварийный таймаут и кнопку остановки.

| Глубина | Ориентир поиска | Максимум шагов | Стартов | Финалистов | Без улучшения, шагов |
| --- | ---: | ---: | ---: | ---: | ---: |
| quick | 15 с | 700 | 1 | 2 | 150 |
| standard | 60 с | 2800 | 2 | 4 | 350 |
| deep | 180 с | 10000 | 4 | 7 | 700 |

Предел шагов делится между стартами. При другой величине бюджета он
масштабируется пропорционально, до 50000 шагов. Для ≤8 задач — максимум
600 шагов и 100 шагов без улучшения; для одной задачи — перебор допустимых
БПЛА и вариантов без отжига. Улучшение времени меньше 0,01 с не продлевает поиск.
Повторяемы маршрут и его метрики, а не служебные timestamps и замеры runtime.
`annealing.solution_sha256` позволяет сравнить решения между запусками.

В интерфейсе выбираются критерий и глубина. Если критерий отсутствовал в
сценарии, выбор добавляет его в редактируемую версию: её нужно сохранить
перед запуском. Значение выбранного критерия крупно показывается в «Обзоре»
и на карте. Для неполного решения рядом написано «неполный план» и число
неназначенных задач. Ход поиска доступен в журнале расчёта.

Python (для совместимости обычный `Settings()` сохраняет прежний режим):

```python
from h2.planner import plan_bundle
from h2.scheduler import Settings

plan = plan_bundle(bundle, Settings(search_depth="standard", time_budget_s=60,
                   objective="makespan", seed=20260918), scene_sidecar)
```

CLI:

```bash
python -m h2 plan bundle.json --scene scene.json --search-depth standard \
  --time-budget 60 --objective makespan --out /tmp/h2-plan
```

`--legacy` включает прежний CP-SAT/LNS. Параметр `--iterations` относится
только к нему. API `POST /api/v1/plans` принимает `search_depth`, `objective`,
`time_budget_s`, `seed`; его режим по умолчанию — `standard`, 60 с, 20260918.

## Замеры 26.09.2026

Это замеры текущего сервера, а не обещание времени для любых входов.

- S05, две задачи / два БПЛА, standard: **1504,98 → 952,18 с** по времени
  завершения (−36,7%). Полный H1 → H2 → H3 занял **3,74–3,93 с**,
  `SAFE`, покрытие 100%. Два запуска дали один SHA-256 решения.
- Искусственный тест с одним БПЛА и восемью задачами, чередующимися между
  удалёнными группами: **4487,96 → 2027,02 с** для обоих критериев (−54,8%) относительно
  начального H2, весь расчёт H2 **0,43–0,49 с**. Это тест H2; H3
  для искусственного bundle не заявляется. Порядок задач действительно меняется.
- S17 `alotofZones`, 117 задач / 384 галса / три БПЛА, standard: подготовка
  **6,17 с**, прежний начальный H2 **32,76 с**, отжиг **15,08 с**,
  подробные финалисты **24,68 с**. Сам H2 — **78,67 с**.
  H1, H2 и подготовка фактических метрик H3 — **122,33 с**;
  независимая повторная проверка H3 — **44,58 с**; всего **166,91 с**.
  Существующий веб-сервис после неуспешного результата может отдельно
  пересчитывать рекомендации с изменёнными исходными условиями; это
  дополнительное время не входит в приведённый замер основного плана.

S17 пока **не решён полностью**: у прежнего H2 назначено 72/117 задач,
у консервативных финалистов — 48/117. Выбран более полный прежний результат;
45 задач остаются неназначенными. H3: `UNSAFE`, покрытие около 79,90%,
сертификата нет. Запас сеточной модели не ослаблялся. Улучшение оценки
неполного сеточного плана (38517 → 28477 с, 46 → 48 задач) нельзя выдавать за
ускорение полной миссии. Невозможность полного решения здесь не доказана.


могут отличаться. Скрипт сохраняет кандидат, заключение H3, журнал и сводку.
