# H2: Routing Solver по отдельным галсам

Рабочий контур: `/root/h3`, dev-сайт `https://45.87.246.124:9443/`.
Постановка и исходные сообщения: [routing-solver-task.md](routing-solver-task.md).

## Вход и неизменяемая геометрия

`h1_coverage.transect_bundle.export_transect_bundle` переводит группы H1 v1/v2
в `gmp.h1_h2.v3`. Каждый полный галс — отдельная задача, с `parent_task_id`,
`transect_id`, `transect_index`; `parent_tasks` сохраняет оригинал. Координаты,
AGL и требования датчика копируются. Контракт проверяет полный набор галсов,
соответствие оригиналу и отсутствие подмены требований. H1 не назначает борт.
Ограничения целой группы по длительности/разворотам пересматриваются для галса;
остальные явные исключения сохраняются.

## Граф и предрасчёт

`routing_graph.py`: физические вершины — концы галсов и действующие базы.
Соседние галсы соединены по обеим сторонам; ориентация исходных линий учитывается.
Помимо крайних галсов каждой группы, права угловых точек получают оба конца
промежуточных галсов. Интервал вдоль края шире 300 м делится по существующему
галсу, ближайшему к середине физической длины интервала; деление повторяется
для обеих половин. При равенстве выбирается первый галс. Для неровного края
используется накопленная длина с максимумом расстояний двух сторон на каждом
шаге. Например, три галса через 250 м дают шесть точек входа/выхода, включая
оба конца среднего галса. Новые координаты и галсы не создаются: если даже
соседние галсы отстоят более чем на 300 м, меньший шаг недостижим без правки H1.
Все выбранные точки участвуют в тех же базовых и межгрупповых связях ниже.
Углы групп соединяются с K=4 соседями из других групп. Дополнительно каждый
угол предлагает не более двух дальних связей: кандидаты делятся на две полосы
дальности, в каждой выбирается дальний конец с предпочтением нового направления.
Равенства разрешаются стабильным порядком вершин. Всего не более `2 × C`
дополнительных неориентированных пар; клика не строится.
**Каждая действующая база соединена со всеми углами**, оба направления
проверяются отдельно. **Связей база—база нет**. Физический путь не проходит
сквозь базу: посадка и следующий вылет требуют явного узла обслуживания.
Параллельные соседние галсы одной зоны продолжают забор через границы чанков H1.
Если компонента не достигает базы, добавляются проверенные связи между углами.
Dummy-вершин в физическом графе нет.

Для каждого полного профиля БПЛА отдельно считаются оба направления рёбер:
обход препятствий, DEM, AGL, ограничение вертикальной скорости, время манёвра.
Время транзита и поворотов считается без процентной надбавки. Межгрупповые и базовые перелёты имеют
дополнительный подъём 30 м; короткие связи забора его не повторяют. Галсы
проходятся по исходной полилинии с полной проверкой высот. Затем Dijkstra
готовит пути, времена и пороги ресурса. Состояние хранит входящее ребро и курс:
повороты учитываются на стыках и при входе/выходе из галса, а не полным кругом
на каждом ребре. В callback солвера нет расчёта геометрии.

В транзите строится верхняя вогнутая огибающая профиля AMSL: аппарат может
пролетать над впадинами, не повторяя каждое изменение DEM. Она нигде не ниже
исходной проверяемой полилинии, сохраняет высоты концов и ограничения скоростей.
Используется только если даёт выигрыш. Для **съёмки**
такое сглаживание запрещено: исходная AGL H1 сохраняется полностью.

Для фрагмента `Q=max(prefix + return + margin)` — требуемый остаток **на входе**,
а фактический расход равен времени фрагмента. Дополнительный запас возврата —
60 секунд. Возврат из внутренних точек гарантируется конструктивно: можно
долететь до следующего проверенного конца ребра/галса и далее до реальной базы.
Это консервативнее поиска кратчайшего аварийного пути из каждой внутренней точки.
Взлёт и посадка учтены отдельно. Возврат может завершаться на любой действующей
посадочной/резервной площадке; обслуживание и повторный взлёт — только согласно
`refuel_sites`. Резервная посадка не даёт бесплатной зарядки.

## Модель Routing

`routing_solver.py`: одна машина — один физический БПЛА на всю миссию.
Каждому галсу соответствуют `g+` и `g−`; обязательная дизъюнкция требует ровно
одно посещение одной из них. Совместимость задаётся отдельно для каждого борта.
Стоимость исходящей дуги включает **полное обслуживание текущего галса** и
путь до следующей операции, включая последний галс перед посадкой.

Физические промежуточные точки могут проходиться многократно. Логические узлы
обслуживания — отдельные конечные копии посещений базы. Начальное число копий
зависит от работы и ёмкости; при исчерпании копий в неполном начальном плане
граница удваивается и поиск повторяется. Неудача при конечной границе копий
не является доказательством физической невозможности.

Размерности:

- `Time`: полёт, обслуживание, ожидания на земле; окно миссии и временные окна.
- `Fuel`: использованное время вылета, ёмкость `endurance × (1 − reserve)`.
  Сброс происходит только в узле настоящей посадки с последующим обслуживанием.
- `Home`: сохраняет старое правило одной базы для входов без нового поля.
- Дополнительное табличное ограничение: потреблённый ресурс + Q выбранной дуги
  не превышает ёмкость выбранного борта. Q не прибавляется повторно к расходу.

Dummy-старт имеет только выход в разрешённую начальную базу, dummy-финиш —
только вход из конечной. Последовательные посещения реальных баз без задачи
между ними запрещены, включая перелёт через транзитные вершины.
Неиспользованный БПЛА может иметь пустой маршрут.

Оптимизация `makespan` минимизирует общий конечный момент (`Time` с общим нулём),
`total_flight` — сумму времени полёта, без наземных ожиданий и зарядки.
При одинаковом округлённом makespan второй критерий — суммарный налёт:
свободный запас времени остальных бортов не поощряет бессмысленные перелёты.
Длительности округляются вверх до 0,1 с, ёмкости вниз; подробные траектории
и окончательные метрики сохраняют исходную точность.

Начальное решение выбирается из четырёх компактных вариантов: параллельная
группа целиком одному БПЛА либо разделение на соседние полосы, каждый вариант
в двух направлениях обхода. Группируются галсы одного задания, профиля датчика,
высоты и направления съёмки, в том числе через границы чанков H1.
Сначала назначаются группы с меньшим числом доступных бортов. Распределение
стремится к AAAABBBB вместо ABABABAB; явные ограничения доступности имеют
приоритет. Направления галсов и зарядки для заданного порядка подбираются
по реальным таблицам поиском с ограниченным Парето-фронтом.
Лучший допустимый компактный вариант становится стартом. Жадный вариант
служит запасным стартом при отсутствии допустимого компактного и сохраняется
среди кандидатов на финальную проверку. Все варианты ранжируются по настоящей
целевой функции, без надбавок за дробление зон. Поле `selected_seed` показывает
выбранный старт. Связность полос не становится обязательным ограничением solver.
Далее OR-Tools Routing применяет Guided Local Search. Seed фиксирован: 20260918,
один поток. Верхний предел поиска задаётся числом ветвей (1200/5000/15000 для
quick/standard/deep, масштабируется бюджетом 15/60/180 с); для ≤8 галсов
не более 600. Дополнительный детерминированный предел обращений к таблицам:
100000/400000/1500000, также масштабируется бюджетом. Сохраняются 2/4/7 лучших
различных физических маршрутов; перестановки одинаковых копий базы не создают
новый вариант. В отчёте отдельно
отмечен аварийный предел времени: он не является обещанием воспроизводимости
на машине, где поиск был прерван этим пределом. Между версиями OR-Tools
тождественность результата также не обещается.

## Перестановки целых блоков галсов

После поиска OR-Tools `routing_blocks.py` улучшает лучший табличный маршрут
тремя операциями: упорядочить принадлежащие борту параллельные галсы по
поперечной координате, передать весь такой блок другому совместимому борту,
обменять два блока между бортами. Для каждого блока пробуются оба порядка.
Блок объединяет одну зону, профиль датчика, высоту и направление съёмки,
в том числе через границы чанков H1 и промежуточные зарядки.

Для изменённых последовательностей `sequence_route` заново выбирает направления
прохода и разрешённые зарядки по готовым таблицам. Оценка включает перелёты,
обслуживание, расход и порог возврата Q. Неизменившиеся последовательности
кэшируются. Перестановка принимается только при строгом улучшении выбранной
метрики с прежним вторичным критерием, сохранении всех задач и допустимости
датчиков, ресурса и баз. Временные конфликты проверяет завершающий этап.

Поиск детерминирован: до трёх проходов, 80/320/1000 новых оценок маршрута
для quick/standard/deep. Для переноса рассматриваются три ближайшие границы
существующих блоков; это ограниченная окрестность, а не доказательство оптимума.
Четыре последних улучшения участвуют в отборе финалистов. `block_search`
содержит принятые операции, число оценок и время. Операции не меняют геометрию
H1 и не вводят штрафов за внешний вид маршрута.

Для полного покрытия API запрашивает у H1 порог 100%. H1 проверяет физическую
прямоугольную полосу датчика и при необходимости достраивает параллельные
проходы у границ зоны внутри разрешённого воздушного пространства.
Круглые торцы буфера больше не засчитываются как фактически снятая площадь.
H2 получает уже готовые галсы; окончательное покрытие независимо проверяет H3.

## Единый автоматический запуск в интерфейсе

На 9443 пользователь выбирает только метрику. Выбор глубины и поле бюджета
убраны. Запрос без технических переопределений получает `search_depth=deep`
и `time_budget_s=180`: до 1,5 млн обращений к таблицам, 1000 оценок блоков,
7 финалистов и прежний глубокий лимит разведения 16. Эти значения задают
верхний объём работы, а не обязательную длительность расчёта.

Поиск Routing завершается раньше после 400 тыс. обращений к таблицам без
строгого улучшения лучшей допустимой табличной оценки. При улучшении отсчёт
начинается заново. Равные и худшие решения его не сбрасывают. До появления
допустимого кандидата этот критерий отключён. Для сцен до 8 галсов терпение
ограничено 20 тыс. обращений; прежний предел 600 ветвей также действует.
В технических режимах терпение масштабируется бюджетом и ограничивается
общим пределом обращений. Блочный поиск по-прежнему заканчивается после
прохода без принятых улучшений, максимум трёх проходов или исчерпания лимита.

`stagnation_read_limit`, `reads_since_improvement` и
`stagnation_limit_reached` в отчёте позволяют проверить раннюю остановку.
Критерий детерминирован и относится к стоимости до разведения: он не доказывает
оптимальность окончательного расписания. Seed, геометрия, модель времени,
ресурсные ограничения и независимые проверки H3 сохранены. Параметры
`search_depth` и `time_budget_s` доступны через API для экспериментов.
Браузерные прогоны S18 и сертификаты: [evidence](../../docs/evidence/h2-automatic-search/README.md).

## Завершающий этап

После выбора проверенного финалиста выполняется дополнительное сокращение
транзита. Сначала проверяется прямая между концами всей цепочки транзитных
рёбер; если она не подходит, проверяются пары соседних рёбер с повторным
просмотром после успешного сокращения. Галсы съёмки, взлёты, посадки и посещения
баз не удаляются. Прямые рассчитываются общей функцией физических рёбер:
проверка воздушного пространства с буфером, DEM, высоты концов, подъём транзита,
верхняя огибающая высот и скорости. В сравнении времени учтены повороты на
стыках с оставшимся маршрутом, включая вход в следующий галс.

Для сокращённой цепочки заново считается достаточный ресурс: в любой внутренней
точке можно долететь до сохранённого конца ребра, развернуться в направление
проверенного возврата и долететь до реальной базы с прежним запасом 60 с.
После сокращения повторяются разведение и полная проверка H2. Если они не
прошли или выбранная метрика ухудшилась, сохраняется исходный проверенный
финалист. При равенстве главной метрики допускается улучшение второй.
Итог по-прежнему поступает на независимый H3. Это локальная оптимизация;
глобальный Routing повторно не запускается. Статистика и метрики до/после
записываются в `routing.transit_shortcuts`.

`routing_planner.py` восстанавливает подробные траектории из тех же физических
рёбер и галсов, разбивает миссию на вылеты в настоящих узлах обслуживания.
Старый `repair_schedule` сдвигает вылеты на земле для устранения столкновений
и временных запретов, переносит последующие вылеты того же борта и проверяет
окна. Затем независимые проверки H2 и штатный независимый H3 проверяют
геометрию, ресурс, возврат, разнесение, покрытие и разрешения баз.

На один кандидат даётся не более 4/8/16 раундов разведения конфликтов
для quick/standard/deep. Неразведённые конфликты остаются ошибками проверки,
после чего рассматривается следующий кандидат. Это детерминированный предел,
защищающий от расходования всего бюджета worker на один неудачный маршрут.
Пробная задержка отклоняется сразу после обнаружения первого конфликта пары;
полный отчёт и финальные проверки по-прежнему собирают все конфликты.

После первого проверенного варианта следующие кандидаты сначала сравниваются
по метрике до наземных задержек и числу пропусков. Если даже эта нижняя оценка
не улучшает уже проверенный результат, дорогая проверка кандидата пропускается:
исправление расписания может только добавлять задержки и не добавляет галсы.
Такие пропуски явно записаны в `finalist_checks`.

Если обязательная модель не нашла полного решения, запускается явно помеченный
диагностический поиск с пропусками. Все пропуски перечислены, такой результат
не получает FEASIBLE/SAFE. Неудача эвристики не выдаётся за INFEASIBLE.

## Промежуточная зарядка

Поле каждого БПЛА в `fleet.json`:

| Значение | Поведение |
|---|---|
| `"refuel_sites": null` | Любая действующая база `role=both` |
| `"refuel_sites": ["BASE_1"]` | Только перечисленные базы |
| `"refuel_sites": []` | Без промежуточной зарядки |
| Поле отсутствует | Прежние ограничения сценария сохраняются |

При явном поле `start_site`/`landing_site` задают начало/конец **всей миссии**.
Следующий вылет начинается там, где завершился предыдущий, после
`service_time_s`. В UI можно выбрать любую базу, одну базу или отсутствие
дозарядки; список из нескольких баз поддерживается через JSON-параметры БПЛА.
Кандидатные и только посадочные площадки не предлагаются для дозарядки.

## Карта и проверка

Вкладка «Граф H2» расположена между галсами и маршрутами. Показывает физические
рёбра выбранного профиля, обе направленные операции съёмки, базы и отдельные
направленные административные связи выбора старта/финиша. В popup — времена
по направлениям. Синие стрелки обозначают альтернативы, а не два обязательных
прохода. Финальный выбранный полёт по-прежнему показан на вкладке маршрутов.
Для карты удалены лишние коллинеарные точки с допуском 1 см; подробные 3D-точки
рельефа сохраняются в расчёте и передаются H3. История сцен читает компактные
метаданные SQLite без повторной загрузки всех больших траекторий.

```bash
PYTHONPATH=src:h2/src:h1/h1_coverage/src /root/.venv/bin/python -m pytest h2/tests/test_routing.py -q
PYTHONPATH=src:h2/src:h1/h1_coverage/src /root/.venv/bin/python h2/scripts/benchmark_routing.py \
  --input data/scenarios/S05_multi_uav/input --out /tmp/routing-s05 \
  --objective makespan --repeat
```

## Границы модели

Один кратчайший путь на пару и профиль; альтернативные пути с другим расходом
и временем не образуют полного Парето-фронта. Съёмка внутри временных зон
использует окна в Routing. Временные ограничения транзита проверяются при
восстановлении маршрута; исправление сдвигает вылеты на земле. Альтернативный
обход временной зоны не гарантируется. Конечный KNN-граф и запас возврата
тоже консервативны. Глобальная оптимальность не заявляется. Манёвры имеют ту же
модель времени/геометрии, что существующий контур; это не аэродинамическая
симуляция автопилота. SAFE остаётся заключением H3 по модели.

### Дополнительный поиск по разрешённым окнам

При запрете внутри рабочего времени H2 сравнивает обычный план с последовательным
Routing-поиском по доступным интервалам. В каждом интервале обязательность всех
оставшихся галсов заменяется штрафом за пропуск: сначала максимизируется число
целых галсов, затем оптимизируется выбранная метрика. Пройденные галсы исключаются
из следующего интервала. DEM, физические рёбра и ресурсные таблицы используются
повторно; начальные состояния и базовые разрешения переносятся между окнами.

Вылет должен включать полное возвращение и посадку до закрытия окна. Если подробная
траектория дольше табличной, последние галсы удаляются из этого вылета и остаются
для следующего окна. Ожидание проходит на земле; время обслуживания и фактическая
база предыдущей посадки обязательны. Каждый частичный этап проходит проверку
геометрии, ресурса, временных ограничений и разведения. Затем весь собранный план
проверяется на исходном полном наборе задач. При одинаковой допустимости сравниваются
основная метрика и вторая метрика для разрешения равенства; неполное решение не
заменяет допустимый полный план. Итог по-прежнему проходит независимый H3.

Это дополнительная консервативная эвристика: она не летает во время объединения
всех временных запретов, даже локальных. Обычный поиск сохраняет пространственную
локальность ограничений. Промежуточный конец окна выбирается среди баз, одновременно
допускающих дозарядку и окончательную посадку, чтобы не создавать непроверенный
перелёт между базами при раннем завершении. Это может ограничивать улучшение, но
не ухудшает выбранный допустимый исходный план. Глобальная оптимальность не обещается.

Seed и лимиты работы фиксированы; на окно выделяется ограниченный детерминированный
бюджет поиска. Диагностика `routing.window_search` содержит оба значения метрик,
список интервалов, число выполненных/оставшихся галсов, проверки и причину выбора.
