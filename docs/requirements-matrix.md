в [current-planning.md](current-planning.md). Эта таблица описывает
дополнительные инженерные требования команды, а не текст оригинального PDF.

| № | Требование | Реализация и доказательство |
| --- | --- | --- |
| 1 | Отдельные алгоритмы, примеры, CSV | `algorithms/catalog.json`, `examples`, `scripts/evaluate_algorithms.py`, `scripts/benchmark_algorithms.py` |

## Что проверяют метрики

CSV каждого алгоритма показывает реальные test case, исход теста, время
выполнения и хеш исходника. `cross_scenario.csv` содержит отдельные замеры
площади покрытия, длины, налёта, makespan, конфликтов и разных seed.
Повторное использование интеграционного теста несколькими алгоритмами не
увеличивает общее число уникальных тестов.

Обучаемой модели нет: k-fold или точность на обучающей выборке здесь не
определены. Используются независимые сценарии, отрицательные случаи и
несколько seed. Ни проход тестов, ни совпадение с эталоном не доказывает
глобальную оптимальность или отсутствие ошибок на любом возможном входе.

Например, примитив sweep при наклонном направлении может дать неполное
покрытие. В CSV этот результат сохранён. Выбор полного кандидата и H3 gate
не допускают выдачу SAFE для такого неполного покрытия. На это есть
специальные регрессионные и mutation-тесты.

## Границы испытаний

Нагрузочный тест запускает отдельный API с PostgreSQL и настоящими LIVE
расчётами S00. Он не моделирует одновременно 32 тяжёлых миссии по 100 км²:
очередь имеет предел, избыток заявок получает контролируемый 429.
Отчёт хранит фактическое железо, p95 HTTP, статусы заданий и пиковый RSS
API/worker. Память PostgreSQL измерением RSS дерева API не охвачена.

Старый `gmp.planner` не входит в LIVE-цепочку. Исторические benchmark/conformance
проверки этого пути отделяются от результатов канонического H1/H2/H3, а не
выдаются за проверку текущего сервиса. Основной набор проверок задан в CI.
