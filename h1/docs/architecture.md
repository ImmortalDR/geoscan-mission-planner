## 1. Зачем вообще существует H1

Весь продукт Geoscan — это **предполётный планировщик групповых авиаработ**. Пользователь приносит карту и флот; система должна вернуть безопасный план: кто, куда, когда летит.

Это слишком большая задача для одного модуля. Поэтому пайплайн разрезан на три зоны:


| Зона                    | Вопрос, на который отвечает                      | Пример                                      |
| ----------------------- | ------------------------------------------------ | ------------------------------------------- |
| **H1** Scene & Coverage | *Что* надо снять и *как* геометрически покрыть?  | «Вот 120 маленьких кусков съёмки с галсами» |
| **H2** Optimize & 4D    | *Кому* отдать куски и *в каком порядке/времени*? | «БВС-3 делает T014→T015 в 09:40»            |
| **H3** Safety & Export  | *Можно ли это выпускать в небо?*                 | «Сертификат SAFE / UNSAFE»                  |


H1 — это **геометрический и съёмочный** слой. Без него H2 пришлось бы одновременно:

- читать KML/GeoTIFF,
- считать GSD и ширину полосы,
- обходить дыры и запретные зоны,
- учитывать радиус разворота самолёта,
- и ещё решать комбинаторный VRPTW.

Так делают плохо: solver раздувается, GIS-ошибки маскируются под «infeasible», а H2 и H1 нельзя разрабатывать параллельно.

Поэтому H1 **заранее** превращает карту в стабильный артефакт `H1H2Bundle`. H2 получает уже готовые задачи и **не трогает координаты галсов**. Это записано в контракте и проверяется валидатором.

> **Главная идея:** H1 отвечает за «карту → атомарные задачи съёмки»; H2 — за «задачи → расписание флота».

## 2. Словарь: чтобы говорить об одном и том же


| Термин                        | Простыми словами                                                                       | Зачем нужен                                                           |
| ----------------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| **Сцена (Scene)**             | Всё, что пользователь загрузил про местность: полигон съёмки, дыры, NFZ, площадки, DEM | Единый внутренний объект вместо разрозненных файлов                   |
| **Галс / swath / transect**   | Одна прямая (или почти прямая) линия съёмки «туда» или «обратно»                       | Базовая единица покрытия; камера «пишет» вдоль неё                    |
| **Lawnmower / boustrophedon** | Паттерн «как газонокосилка»: туда–обратно–туда                                         | Классический и понятный способ покрыть площадь                        |
| **Swath spacing**             | Расстояние между соседними параллельными галсами                                       | Определяется шириной кадра и боковым перекрытием                      |
| **GSD**                       | Ground Sampling Distance — сколько см земли в одном пикселе                            | Качество съёмки; от него считается высота полёта                      |
| **Overlap (перекрытие)**      | Насколько соседние кадры/полосы накладываются                                          | Нужно для склейки ортофото / стерео; уменьшает полезную ширину полосы |
| **AGL**                       | Above Ground Level — высота над рельефом, не над уровнем моря                          | Безопасность и корректный GSD на холмах                               |
| **NFZ**                       | No-Fly Zone — зона, куда лететь нельзя                                                 | Hard constraint: галс не должен её пересекать                         |
| **Hole (дыра)**               | Отверстие внутри полигона съёмки (озеро, здание, чужой участок)                        | Нужно покрыть «вокруг», не лететь внутрь                              |
| **AtomicTask**                | Небольшой кусок работы: группа галсов + вход/выход + длина + payload                   | То, чем оперирует solver H2 вместо «80 км одной полилинии»            |
| **Feasibility**               | Таблица «какая задача какому БВС вообще разрешена»                                     | H2 не должен угадывать GIS/payload-логику                             |
| `fixed_wing_safe`             | Флаг: хватает ли места на разворот самолёта у края галса                               | Самолёты не умеют разворачиваться на месте                            |
| `H1H2Bundle`                  | JSON-конверт: сцена + флот + задачи + feasibility                                      | Единственный шов между H1 и H2                                        |
| **CRS / метры**               | Система координат: внутри планировщика всё в метрах UTM                                | В градусах нельзя честно считать длины и буферы                       |

## 3. Что пользователь даёт и что получает команда



### Вход (то, с чем работает H1)

1. **Геометрия местности** — GeoJSON / KML: граница съёмки, отверстия, NFZ, площадки старта/посадки.
2. **Рельеф (опционально)** — GeoTIFF DEM. Если нет — считаем землю плоской (явно пишем warning).
3. **Требования к съёмке** — тип нагрузки (RGB, LiDAR, …), желаемый GSD, перекрытия, профиль камеры.
4. **Флот и условия** — список БВС (из KB), ветер, окна миссии (H1 читает ветер для scoring и feasibility; расписание дней — зона H2).



### Выход (единственный артефакт для H2)

Файл вида `fixtures/h1_h2/<scene_id>.bundle.json` — объект `H1H2Bundle`:

- `tasks[]` — атомарные задачи с галсами в **метрах**;
- `fleet[]`, `sites[]`, `mission` — то, без чего H2 не стартует;
- `feasibility` — кто *вообще* может делать задачу (payload, ветер, fixed-wing);
- `crs` — в какой UTM-зоне лежат координаты;
- `warnings[]` — мягкие проблемы (нет DEM, обрезали галсы у NFZ и т.п.).

Подмена «фейк → живой coverage» = замена того же файла. Код H2 **не ветвится** на fake/real.

## 4. Почему архитектура именно такая



### 4.1. Почему «атомарные задачи», а не один огромный маршрут

Если отдать H2 одну полилинию на 200 км, solver почти ничего не может:

- нельзя передать половину другому БВС;
- нельзя вставить посадку/замену батареи посередине;
- нельзя поменять порядок кусков независимо.

В литературе multi-UAV coverage почти всегда делит площадь на **ячейки / chunks / cells**, а потом решает assignment (см. SC-VRP `arxiv:2007.13065`, EnergyAwareMCPP `arxiv:2402.10529`). Мы делаем то же: H1 режет покрытие на `AtomicTask`, H2 их назначает.

Группировка «по 5 галсов» или «не длиннее X метров» — инженерный рычаг: слишком мелкие задачи → combinatorial explosion; слишком крупные → плохое балансирование флота.

### 4.2. Почему метры, а не lon/lat

В WGS-84 «1°» — разная длина в метрах на разных широтах. Буфер 50 м вокруг NFZ, длина галса, радиус разворота — всё это **метрические** величины. Контракт жёстко требует: внутри bundle только метры одной UTM-зоны. Lon/lat остаются на границе IO (загрузка/экспорт).

### 4.3. Почему H1 считает eligible, а не H2

Совместимость «камера ↔ БВС», «ветер ↔ max_wind», «разворот ↔ NFZ» — GIS/KB знание. Если каждый solver будет пересчитывать это по-своему, появятся расхождения. H1 отдаёт матрицу `eligible_uav_ids_by_task`; H2 может только **ужесточать** (например, не хватает энергии на весь день), но не расширять список.

### 4.4. Почему несколько углов галсов (candidates)

Один угол «север–юг» часто хуже другого: больше разворотов, хуже относительно ветра, длиннее суммарный путь. Fields2Cover и практика survey (QGC) перебирают направления. H1 оставляет top-K кандидатов (или лучший + метаданные), чтобы H2/человек могли сравнить. В MVP контракта objectives у H2 только `makespan` | `total_flight` — кандидаты покрытия помогают косвенно (короче survey → меньше flight).

### 4.5. Готовые проекты с GitHub — что это и зачем они нам

В интернете уже есть программы, которые умеют куски нашей задачи. Мы **не пишем всё с нуля** и **не подключаем чужую программу целиком вместо нашего продукта**.

Аналогия: нам нужен свой ресторан (Geoscan-планировщик).

- Где-то продают хорошую овощерезку — берём её (библиотека).
- Где-то есть целая чужая кухня под другой бренд — смотрим рецепты, но не переезжаем в их здание.

Ниже — пять таких «готовых кухонь/инструментов» простыми словами.

---



#### Fields2Cover — «опциональный станок» (не production path)

**Что это.** Открытая библиотека для покрытия поля линиями.  
Сайт/код: [https://github.com/Fields2Cover/Fields2Cover](https://github.com/Fields2Cover/Fields2Cover)

**Статус в H1 (честно):** production coverage = **DIY lawnmower** на Shapely (`diy_lawnmower_v1`).  
Нативный `fields2cover` может быть установлен, но **геометрический bridge Shapely↔F2CField не подключён** — адаптер не маскирует DIY под F2C.

**Что берём сейчас:** идеи (углы, headlands, кинематика) + optional dep в `[f2c]`.  
**Что планируем позже:** реальный bridge на `SG_BruteForce` / Dubins из F2C.  
**Чего не берём:** multi-robot assignment F2C (это **H2**); их JSON вместо `H1H2Bundle`.

**Итог:** Fields2Cover = *целевой* станок галсов, не заявленный текущий engine.

---



#### ETH polygon_coverage_planning — «как резать поле с дырами»

**Что это.** Научный планировщик покрытия от ETH Zurich: полигон, внутри деревья/дыры, дрон облетает.  
Код: [https://github.com/ethz-asl/polygon_coverage_planning](https://github.com/ethz-asl/polygon_coverage_planning)

**Слова, которые там встречаются:**

- **BCD** — разрезать сложную фигуру на простые куски (ячейки), в каждом своя змейка;
- **GTSP** — потом выбрать, в каком порядке эти куски обходить (оптимизация маршрута по ячейкам).

**Что берём мы:** только **идеи и статьи** (как резать полигон с отверстиями).

**Чего не берём:** весь их софт целиком. Он завязан на **ROS** (робототехническая ОС) и тяжёлую геометрию **CGAL**. Для хакатона это как тащить целый комбайн, чтобы нарезать салат.

**Итог:** читаем и повторяем подход упрощённо на Shapely; не ставим их стек.

---



#### QGroundControl (QGC) — «приложение пилота, из которого берём формулы»

**Что это.** Популярная наземная станция для дронов: нарисовал полигон на карте — получил mission с галсами.  
Код: [https://github.com/mavlink/qgroundcontrol](https://github.com/mavlink/qgroundcontrol)

**Что берём мы:** как они из **GSD** и **перекрытия** считают высоту и расстояние между галсами (школьная геометрия камеры). Смотрим код/доки survey, **не** встраиваем QGC.

**Чего не берём:** их интерфейс, прошивку, «нажми кнопку — лети». Мы делаем свой сервис планирования группы БВС, не клон QGC.

**Итог:** QGC = учебник по формулам съёмки для модуля SurveyModel.

---



#### DARP — «разрежь площадь между роботами поровну»

**Что это.** Алгоритм: есть сетка клеток и несколько роботов — кому какая клетка.  
Код: [https://github.com/athakapo/DARP](https://github.com/athakapo/DARP)

**Что берём мы:** максимум как **простой baseline** «можно делить территорию». Для сравнения / демо «тупой способ».

**Чего не берём как основу H1:** у DARP единица работы — **клетка сетки**. У нас единица — **AtomicTask** (группа галсов съёмки с камерой, AGL, NFZ). Это разные миры. Подменять одно другим = сломать стык с H2.

**Итог:** знать, что существует; не строить на нём ядро.

---



#### EnergyAwareMCPP — «учёт батареи при покрытии несколькими дронами»

**Что это.** Планировщик multi-UAV coverage с оценкой энергии и скорости.  
Код: [https://github.com/ctu-mrs/EnergyAwareMCPP](https://github.com/ctu-mrs/EnergyAwareMCPP)

**Что берём мы:** идеи, **как грубо оценить**, хватит ли ресурса на кусок работы (для scoring / feasibility).

**Чего не берём:** их полный «кто когда вылетает, несколько вылетов, расписание». Это как раз зона **H2**.

**Итог:** справочник по энергии; планировщик вылетов пишем сами в H2.

| Имя             | Простыми словами            | Наша роль                             |
| --------------- | --------------------------- | ------------------------------------- |
| Fields2Cover    | Станок галсов (идеи / future) | Production = DIY; F2C bridge TBD    |
| ETH coverage    | Умная нарезка поля с дырами | Копируем идеи, не весь софт           |
| QGroundControl  | Приложение пилота           | Воруем формулы GSD, не UI             |
| DARP            | Делёж сетки между роботами  | Только baseline, не наша модель задач |

Принцип из ТЗ: *GitHub помогает сделать наше ТЗ, но не подменяет ТЗ.* Мы собираем **свой** конвейер под `H1H2Bundle`, а чужие проекты — запчасти и учебники.

### 4.6. Почему fixed-wing отдельно от мультикоптера

Мультикоптер может развернуться почти на месте. Самолёт (fixed-wing) требует дуги разворота с радиусом порядка `turnaround_buffer_m`. Галс может «влезть» в коридор, а разворот — врезаться в NFZ. Поэтому H1 ставит флаг `fixed_wing_safe` и выкидывает самолёты из eligible, если места нет (сценарий приёмки S08). Это дешевле, чем чинить геометрию уже в H2.

## 5. Общая схема потока данных

Ниже — логический конвейер. На практике часть шагов идёт параллельно (KB загружается независимо от DEM), но **зависимости** такие:

```
Файлы пользователя (KML / GeoJSON / GeoTIFF)
         │
         ▼
  ┌────────────┐     PyProj
  │ SceneLoader│ ──────────────→  WGS-84 → метры CRS (UTM)
  └──────┬─────┘
         │ Scene: полигон + holes + NFZ + sites + путь к DEM
         ▼
  ┌────────────────┐
  │  TerrainModel  │  высота земли в точке → корректный AGL
  └──────┬─────────┘
         │
         ▼
  ┌───────────────┐
  │   UAV KB      │  характеристики бортов и payload
  └──────┬────────┘
         │
         ▼
  ┌────────────────┐
  │  SurveyModel   │  GSD/overlap/камера → высота и ширина полосы
  └──────┬─────────┘
         │
         ▼
  ┌──────────────────────────────────────────────────────────┐
  │  CoverageEngine  (DIY lawnmower; optional F2C later)     │
  │   полосы покрытия под заданным углом + развороты         │
  └──────┬───────────────────────────────────────────────────┘
         │
         ▼
  ┌─────────────────────────────────────────────────────┐
  │  DecompositionEngine  (идеи ETH BCD)                  │
  │   сложный полигон с дырами → выпуклые ячейки          │
  └──────┬──────────────────────────────────────────────┘
         │
         ▼
  ┌────────────────────────────────────────────────────────┐
  │  NFZManager                                              │
  │   вырезать запретные зоны, проверить G1                  │
  └──────┬─────────────────────────────────────────────────┘
         │
         ▼
  ┌────────────────────────────────────────────────────────┐
  │  FixedWingBuffer                                       │
  │   хватает ли места на разворот самолёта                │
  └──────┬─────────────────────────────────────────────────┘
         │
         ▼
  ┌─────────────────────────────────────────────────────────┐
  │  CoverageCandidateGenerator                             │
  │   несколько углов → ranking (ветер, длина, развороты)   │
  └──────┬──────────────────────────────────────────────────┘
         │
         ▼
  ┌─────────────────────────────────────────────────────────┐
  │  AtomicTaskBuilder                                      │
  │   группы галсов → AtomicTask[] под контракт             │
  └──────┬──────────────────────────────────────────────────┘
         │
         ▼
  ┌───────────────────────────────────────────────────────────┐
  │  FeasibilityMatrix                                        │
  │   кто из флота вообще может делать каждую задачу          │
  └──────┬────────────────────────────────────────────────────┘
         │
         ▼
  ┌─────────────────────────────────────────────────────────┐
  │  BundleExporter                                         │
  │   собрать JSON + проверить G1…G7 → файл для H2          │
  └─────────────────────────────────────────────────────────┘
                    │
                    ▼
              H1H2Bundle  →  H2
```

**Важно про порядок Coverage vs Decomposition.** На схеме Decomposition стоит после «сырого» coverage engine — это отражает *роли*. На практике для полигона с дырами сначала режут ячейки (M7), потом в каждой ячейке гоняют генератор полос (M6). Для простого выпуклого прямоугольника декомпозиция почти noop: одна ячейка = весь полигон.

## 6. Файловая структура (куда класть код)

**Канон H1 (с 2026-09):** пакет [`h1/h1_coverage/`](h1_coverage/) — не дублировать алгоритмы в `gmp/coverage`.

```
h1/h1_coverage/src/h1_coverage/
├── io/
│   ├── scene.py              # M1 SceneLoader (каталог → Scene)
│   ├── dem.py                # M3 DEM / local AGL checks
│   ├── geojson.py / kml.py   # входы GeoJSON + KML fallback
│   ├── encoding.py           # BOM / UTF-16 / size cap
│   ├── inspect.py            # CLI inspect
│   └── manifest.py           # реестр входных файлов
├── geo.py                    # M2 CRS, метры, lon/lat heuristic
├── kb/
│   ├── catalog.py            # M4 UAV KB
│   └── seed.yaml             # Geoscan MVP + passport vs operational
├── coverage/
│   ├── survey.py             # M5 GSD → AGL, swath
│   ├── sweep.py / backend.py # M6 DIY lawnmower (+ optional F2C status)
│   ├── decomp.py             # M7 BCD merge/order
│   ├── exclusions.py         # M8 NFZ / obstacles
│   ├── fixed_wing.py         # M9 развороты
│   ├── candidates.py         # M10 multi-angle
│   ├── atomic.py             # M11 AtomicTaskBuilder
│   ├── corridor.py           # LineString → corridor
│   └── engine.py             # оркестрация coverage
├── feasibility.py            # M12
├── bundle.py                 # M13 H1H2Bundle
├── pipeline.py / cli.py
└── models.py                 # внутренние типы (шов наружу — bundle)
```

Тонкий bridge в планировщике: `h3/src/gmp/coverage/` → `h1_coverage.pipeline.run_h1`.  
Входы: [`docs/inputs.md`](docs/inputs.md). Live bundles: `fixtures/h1_h2/*.bundle.json`.

`models` в bundle и формат `fixtures/h1_h2/*.bundle.json` — **замороженный шов**. Алгоритмы внутри `coverage/` можно менять свободно; поля `AtomicTask` — нет.

## 7. Модули: что / зачем / почему так / откуда знание



### M1 — SceneLoader

**Что.** Читает GeoJSON/KML/GeoTIFF и собирает один объект `Scene`: граница, дыры, NFZ, площадки, ссылка на DEM, параметры миссии.

**Зачем.** Дальше все модули должны работать с одной валидной геометрией, а не каждый раз парсить файлы по-своему. Ошибки «битый полигон» и «площадка вне зоны» ловятся здесь, а не в solver.

**Почему так.** Готовые GDAL/GeoPandas умеют форматы; *наш* код — правила обязательности («без boundary нет смысла»), нормализация MultiPolygon, человекочитаемые ошибки. Это то, чего нет «в библиотеке из коробки».

**Тесты-ориентиры:** S00 (простой полигон), S02 (дыры).

---



### M2 — GeoProjector

**Что.** Переводит геометрию из WGS-84 в метрическую UTM зоны сцены; хранит `metric_epsg` в bundle.

**Зачем.** Длины галсов, буферы NFZ, радиусы разворота — в метрах. H2 запрещено перепроецировать задачи: иначе «поедут» все длины.

**Почему так.** PyProj — стандарт; автоопределение зоны по центроиду сцены — обычная практика. Эвристика контракта: если все координаты похожи на lon/lat (`|x|≤180`, `|y|≤90`) — это ошибка, не «метры около нуля».

**Тест:** round-trip туда-обратно с погрешностью ≪ 1 м.

---



### M3 — TerrainModel

**Что.** По координате (x, y) в метрах отдаёт высоту земли; помогает согласовать AGL.

**Зачем.** На холме «120 м над уровнем моря» может оказаться 20 м над землёй — опасно и ломает GSD. ТЗ: рабочая высота задаётся AGL; точный terrain-following в полёте — у автопилота, но *планировать* без DEM нельзя честно.

**Почему так.** Rasterio читает GeoTIFF. Если DEM нет — flat=0 и warning (демо не блокируем). Идеи сглаживания/досэмплирования — из terrain-following CPP (`arxiv:2601.00614`, адаптер поверх 2D — `arxiv:2507.17519`).

**Не путать:** H1 не пишет полный 3D spline полёта; H1 задаёт `agl_m` задачи и опирается на DEM для проверок/предупреждений.

---



### M4 — UAVKnowledgeBase

**Что.** Версионируемый каталог БВС и payload: скорость, endurance, max_wind, классы нагрузки, `turnaround_buffer_m`, provenance («откуда цифра»).

**Зачем.** Без KB нельзя заполнить `fleet[]` в bundle и посчитать feasibility. Данные Geoscan проприетарные — в papers их нет.

**Почему так.** YAML + Pydantic: просто править человеком, жёстко валидировать в коде. Provenance обязателен по духу ТЗ (KB): цифра без источника позже «разъедется» между членами команды.

**MVP-модели (контракт §2.4.1):** в seed обязаны быть  
`geoscan_201`, `geoscan_401`, `geoscan_701`, `geoscan_801`, `geoscan_gemini`.  
В одном bundle — любое подмножество; прочие модели только как reference/test.

**Тест:** S11 — RGB-борт не попадает в eligible на LiDAR-задачу.

---



### M5 — SurveyModel

**Что.** Из GSD, overlap и параметров камеры считает рабочую высоту `agl_m` и расстояние между галсами `swath_spacing_m`.

**Зачем.** Пользователь говорит «хочу 3 см/пиксель и 70% бокового перекрытия» — не «лети на 117.4 м с шагом 42 м». Перевод «качество → геометрия полосы» — ядро съёмочной логики.

**Почему так.** Те же соотношения, что в survey-режиме QGroundControl и в обзорах UAS-фотограмметрии (Colomina & Molina). Формулы должны быть с явной проверкой единиц (мм / см / м — классическое место багов).

**Инвариант:** `agl_m ≥ 40` (`MIN_SAFE_AGL_M` в контракте). Если GSD «просит» ниже — поднимаем до минимума и пишем warning (или отказываем — политика команды, но молча нарушать контракт нельзя).

**Интуиция:**

- выше летишь → больше земли в кадре → хуже GSD (крупнее см/пиксель);
- больше overlap → соседние полосы ближе → больше галсов на ту же площадь.

---



### M6 — CoverageEngine (DIY lawnmower; F2C optional later)

**Что.** Для (ячейки) полигона и ширины полосы строит набор параллельных галсов под углом `sweep_angle_deg`. Production path: `DiySweepBackend` / `sweep.generate_transects`.

**Зачем.** Это сердце coverage: без полос нет съёмки. DIY на Shapely закрывает holes/clip/overshoot для handoff H2. Fields2Cover (`arxiv:2210.07838`) остаётся *целевым* native backend после wiring bridge — до этого **не** рекламируем `active=fields2cover`.

**Почему не «вызвали F2C и забыли».** F2C говорит на `F2CField`/`F2CSwath`; пока bridge нет, silent fallback = ложь в diagnostics. Честный статус: `backend_status().fields2cover_bridge_wired == false`.

**Что берём сейчас:** DIY полосы + optional Shapely headland inset; FW turn check в M9.  
**Что не берём:** multi-robot F2C, расписание (H2), подмена имени backend.

---



### M7 — DecompositionEngine

**Что.** Режет сложный полигон (вогнутый, с отверстиями, MultiPolygon) на более простые ячейки, в которых уже честно строится lawnmower.

**Зачем.** На полигоне с озером посередине «тупой» набор параллельных линий даёт обрывки, лишние перелёты и риск залезть в дыру. Классика — **Boustrophedon Cellular Decomposition** (Choset); для UAV с препятствиями — ETH BCD+оптимизация обхода ячеек (`arxiv:1907.09224`). Практичный merge ячеек — в работах про exclusion zones (`arxiv:2411.07053`).

**Почему не тащим весь ETH ROS-стек.** Для хакатона достаточно идей + Shapely. Полный CGAL/ROS — долгая сборка и лишняя связность. Reference-репозиторий: [ethz-asl/polygon_coverage_planning](https://github.com/ethz-asl/polygon_coverage_planning).

**Связь с M6:** декомпозиция → для каждой ячейки CoverageEngine → потом склейка/упорядочивание на уровне задач (M11), не обязательно один глобальный GTSP в MVP.

---



### M8 — NFZManager

**Что.** Расширяет NFZ на safety buffer и вырезает/бракует куски галсов, которые пересекают запретное. В конце — проверка гарантии **G1**.

**Зачем.** Hard NFZ — требование заказчика и ТЗ: SAFE-маршрут никогда не пересекает hard NFZ. Лучше обрезать геометрию в H1, чем надеяться, что H2 «как-нибудь объедет» (H2 геометрию задач не двигает!).

**Почему buffer + difference.** В `arxiv:2411.07053` для exclusion zones используют polygonal offset (straight skeleton) и затем coverage по разрешённой области. В Shapely практичный аналог — `buffer` + `difference` по линиям галсов. Buffer нужен, потому что «линия касается границы NFZ» в реальности всё равно опасно (погрешность навигации, размах крыла).

**Дыры vs NFZ.** Дыра в полигоне съёмки — «здесь не надо снимать». NFZ — «здесь нельзя лететь» (может быть и вне полигона, и внутри). Обрабатываем явно оба случая; не смешивать в одной куче без семантики.

---



### M9 — FixedWingBuffer

**Что.** Для набора галсов оценивает, помещаются ли развороты fixed-wing вне NFZ; пишет `fixed_wing_safe` на задачу.

**Зачем.** Сценарий S08 в приёмке: галс сам по себе ок, а манёвр разворота — нет. Мультикоптеру это всё равно; самолёту — блокер.

**Почему флаг, а не «перерисовать галсы».** Перерисовка меняет покрытие и усложняет детерминизм. Для MVP честнее сказать: «эта задача для FW небезопасна» и убрать FW из eligible (G5). Улучшение геометрии под FW — отдельный эволюционный шаг (можно через `extensions.h1.`*, не ломая schema).

**Опора:** кинематика кривизны / continuous coverage для FW (`arxiv:2505.08382`); в F2C — `Dubins`/`Reeds-Shepp` path planners.

---



### M10 — CoverageCandidateGenerator

**Что.** Пробует набор углов галсов (например 0°…170° шаг 10°), для каждого считает длину, число разворотов, согласованность с ветром; отдаёт top-K.

**Зачем.** Один «дефолтный» угол часто неоптимален. Ветер в ТЗ влияет на ориентацию/score галсов. H2 оптимизирует makespan/total_flight — более короткие/удобные галсы снижают нижнюю оценку налёта.

**Почему scoring простой (веса w1..w3), а не RL.** RL из `arxiv:2505.08382` интересен для research, нестабилен для демо-дедлайна. Достаточно прозрачной эвристики + Fields2Cover brute-force по углам. Энергетическая интуиция — из EnergyAwareMCPP (`arxiv:2402.10529`).

---



### M11 — AtomicTaskBuilder

**Что.** Режет упорядоченные галсы на группы; заполняет все поля `AtomicTask` контракта: id, transects, entry/exit, длины, `turn_count`, `agl_m`, `fixed_wing_safe`, …

**Зачем.** Это **продукт H1 для H2**. Без стабильных id и согласованных entry/exit solver и тесты разваливаются.

**Почему детерминированные id от seed.** Фикстуры и регрессии: один и тот же вход → те же `job#T000`. Иначе «у меня упало на T014» нельзя воспроизвести.

**Инварианты (их же проверяет валидатор):**

- `entry` = начало первого трансекта, `exit` = конец последнего;
- `survey_length_m ≈ sum(transect.length_m)`;
- ids уникальны.

---



### M12 — FeasibilityMatrix

**Что.** Для каждой пары (task, uav) решает: можно / нельзя, и пишет причину отказа.

**Зачем.** H2 не должен знать про payload KB и GIS turn buffer. Матрица — мост. Пустой eligible → задача явно невыполнима (INFEASIBLE), а не «тихо исчезла».

**Что проверяем в H1 (геометрия/совместимость):**

1. класс нагрузки;
2. ветер vs `max_wind_ms`;
3. минимум AGL;
4. `fixed_wing_safe` для самолётов;
5. опционально грубая оценка «длина задачи vs endurance» (ещё не маршрут дня!).

**Что сознательно не проверяем здесь:** окна рабочей недели, multi-sortie с заменой батареи, 4D-конфликты между бортами — это H2 (+ H3). Иначе H1 превратится во второй планировщик.

---



### M13 — BundleExporter

**Что.** Собирает `H1H2Bundle`, гоняет проверки G1…G7, пишет JSON фикстуры/выхода.

**Зачем.** Это «печать паспорта» перед передачей соседям. Красный валидатор = нельзя говорить «H1 готов».

**Команда:** `python h3/scripts/validate_h1_h2_contract.py`

---



## 8. Гарантии H1 перед H2 (G1…G7)

H2 имеет право **верить** этим пунктам и не пересчитывать coverage заново. Повторная независимая проверка безопасности — зона H3.


| ID     | Обещание                                        | Зачем H2 это нужно                                   | Где чинится, если сломалось |
| ------ | ----------------------------------------------- | ---------------------------------------------------- | --------------------------- |
| **G1** | Линии галсов не пересекают hard NFZ             | Иначе любой «оптимальный» план опасен                | M8                          |
| **G2** | `entry`/`exit`/`geom` согласованы с трансектами | Transit и reverse task считаются от правильных точек | M11                         |
| **G3** | Длины положительные, полилинии валидны          | Cost/time не взрываются на NaN/нулях                 | M11 + M13                   |
| **G4** | `agl_m` ≥ 40 и согласован с профилем            | Не планируем заведомо низкий проход                  | M5                          |
| **G5** | Если `fixed_wing_safe=false`, FW нет в eligible | Solver не назначит самолёт в ловушку у NFZ           | M9 + M12                    |
| **G6** | Ids уникальны и стабильны при seed              | Регрессии, дедуп, логи                               | M11                         |
| **G7** | `schema_version = gmp.h1_h2.v1`                 | Несовместимый JSON = hard fail, без best-effort      | M13                         |

## 10. Зависимости между модулями (что от чего ждать)

```
M1 SceneLoader
 ├──→ M2 GeoProjector          (сразу после загрузки)
 ├──→ M3 TerrainModel          (если есть DEM)
 └──→ M4 UAV KB                (можно параллельно)

M2 + требования съёмки → M5 SurveyModel
M1 (+holes) → M7 DecompositionEngine
M5 + ячейки → M6 CoverageEngine
M6 → M8 NFZManager
M8 + M4 → M9 FixedWingBuffer
M5 + M8 + ветер → M10 Candidates
M10 + M9 → M11 AtomicTaskBuilder
M11 + M4 + ветер → M12 Feasibility
всё выше → M13 BundleExporter
```

Минимальный вертикальный срез для первого демо: **M1 → M2 → M5 → M6 → M11 → M13** на прямоугольнике без NFZ (S00). Остальное наращивается, не ломая формат bundle.

## 11. Порядок реализации (зачем такая нарезка дней)

Идея: каждый день заканчивается **проверяемым артефактом**, а не «половиной библиотеки».

### День 1 — каркас IO + пустой/простой bundle

**Зачем первым:** без Scene и CRS нельзя честно тестировать ничего ниже; без экспортёра H2 не может подключаться параллельно.  
**Делаем:** M1, M2, каркас M13, фикстура S00, CLI «coverage-only → число tasks / путь к JSON».

### День 2 — настоящие галсы на простом полигоне

**Зачем:** закрываем главную ценность H1 — автоматическое покрытие.  
**Делаем:** M5, M6, M11; гарантии G2/G3/G6/G7.

### День 3 — реальность карты: дыры, NFZ, DEM

**Зачем:** без этого падают приёмочные S02/S08 и требование 100% coverage без захода в запретное.  
**Делаем:** M3, M7, M8; G1.

### День 4 — флот и запреты

**Зачем:** H2 нужен не только geometry, но и eligible.  
**Делаем:** M4, M9, M12; сценарии S08/S09/S11.

### День 5 — качество покрытия и полный набор фикстур

**Зачем:** ветер/углы и «все S00…S11 зелёные» — демо и стыковка.  
**Делаем:** M10; прогон валидатора на всех bundle.

## 15. Как проверить понимание (мини-FAQ)

**Q: H1 строит полётное задание для автопилота?**  
A: Нет. H1 строит *съёмочные задачи* для оптимизатора. Экспорт KML/QGC plan — после H2/H3.

**Q: Можно ли в H1 сразу назначить лучший БВС на задачу?**  
A: Нельзя как источник истины. Можно подсказать эвристикой в `extensions.h1.*`, но `uav_id` в контракте задачи нет — назначает H2.

**Q: Почему и галсы, и** `AtomicTask`**?**  
A: Галс — геометрия съёмки; AtomicTask — порция работы для solver. Несколько галсов в одной задаче уменьшают размерность VRPTW.

**Q: Что если coverage получился, но eligible пуст у всех задач?**  
A: Bundle всё равно валиден геометрически; миссия для H2 — INFEASIBLE. Это честный результат (не тот флот / ветер / FW+NFZ), а не падение парсера.

**Q: Где «истина» по полям JSON?**  
A: Только `[docs/contract/H1_H2.md](../docs/contract/H1_H2.md)` + `models.py`. Этот файл объясняет *смысл*; контракт фиксирует *форму*.

## 17. Хватит ли этого плана, чтобы выиграть хакатон?

### Главное одной фразой

**Нет — в §1–16 и в плане на 5 дней (§11) заложен рабочий H1 и стыковка с H2, а не «все фичи мира».**  
Выигрыш = этот каркас **плюс** сильный сквозной демо (H1→H2→H3) **плюс** несколько понятных «вау» на экране. Одна только куча фишек в H1 без общего плана жюри не впечатлит.

### Что уже в плане (это и есть основа)

Мы уже задумали и описали:

1. Сами рисуем галсы из карты (не вручную).
2. Учитываем дыры и запретные зоны.
3. Пробуем несколько направлений галсов и ветер.
4. Отдельно думаем про самолёты (разворот).
5. Говорим H2, какие борта вообще могут задачу.
6. Отдаём всё в одном файле `H1H2Bundle`.

Этого достаточно, чтобы **не стыдно стыковаться с H2** и закрыть базовые сценарии S00, S02, S08, S09, S11.

### В каком порядке делать (чтобы не утонуть)

Делайте строго сверху вниз. Нижний уровень без верхнего — пустая трата времени.

**Сначала (обязательно):**  
простой полигон → галсы → задачи → JSON для H2 → команда в терминале работает.  
Без этого нет демо.

**Потом (нужно для «как у заказчика»):**  
рельеф (DEM), дыры, NFZ, самолёты, ветер, база дронов Geoscan, проверка «площадь реально закрыта на 100%», а не только «в NFZ не залезли».

**В конце (бонусы для жюри):**  
красивая карта, таблицы, сравнения вариантов — см. ниже. Только когда первые два пункта уже зелёные.

### Чего в текущем плане ещё нет (дыры относительно ТЗ)

Это не «плохо», это просто **ещё не расписано / не в 5 днях**. Если хотите полноты — добавить после основы:

| Чего нет | Простыми словами | Зачем жюри / заказчику |
|----------|------------------|------------------------|
| Процент покрытия | Мы обещаем не лезть в NFZ, но не считаем явно «вся площадь снята» | Вопрос «а точно 100%?» |
| LiDAR и геофизика | Сейчас мыслим в основном камерой (GSD) | В ТЗ есть другие типы съёмки |
| Узкий коридор (дорога, ЛЭП) | Умеем полигон-поле, не «полосу вдоль линии» | Отдельный тип задач |
| Запретка по времени суток | Геометрия NFZ есть; «с 12:00 до 14:00 нельзя» — скорее H2/H3 | Сценарий S03 |
| Большая сцена ~100 км² | В плане намёк, нет отдельного стресс-теста | Масштаб приёмки S01 |
| Несколько съёмок на одной карте | В примерах часто один job | RGB + LiDAR одновременно |
| Карта в браузере / GeoJSON наружу | В ролях команды есть, в 5 днях слабо | За 30 секунд видно галсы |

### Что добавить именно для «вау» (и это не ломает контракт)

Дешёвые по времени вещи: не меняют поля `AtomicTask`, можно писать рядом (метаданные, картинка, CLI).

1. **Карта с галсами** — открыл HTML, увидел змейку.
2. **Три варианта угла** — таблица: какой короче, где меньше разворотов, какой лучше по ветру.
3. **Число «покрыто N%»** — зелёное/красное на схеме.
4. **Почему борт отказан** — фраза «ветер слишком сильный для 701», а не код ошибки.
5. **Круги разворота самолёта** на карте рядом с NFZ — кейс S08 объясняется за полминуты.

Этих 3–4 пунктов хватит, чтобы H1 на демо выглядел «умным». Больше — по желанию, если останется время.

### Что не надо пихать в H1 «ради плюшек»

Это чужие зоны. Если начнёте — потеряете время и размоете ответственность:

- кто какой дрон и во сколько летит → **H2**;
- сертификат безопасности, «можно ли в небо» → **H3**;
- полная замена QGroundControl / прошивка → не наша цель;
- нейросеть для покрытия из статей → интересно, но не к дедлайну хакатона.

### Практичный список «что ещё сделать», если основа готова

От простого к сложному:

1. Выгрузка галсов в GeoJSON + таблица метрик (длина, число задач).
2. Простая HTML-карта.
3. Отчёт «сравнили 3 угла галсов».
4. Подсчёт процента покрытия площади.
5. По рельефу: предупреждение, если GSD по холмам сильно скачет.
6. Отдельный режим съёмки LiDAR (шаг полос не как у фото).
7. Несколько видов съёмки в одном bundle.
8. Коридорные задачи (дольше всего).
